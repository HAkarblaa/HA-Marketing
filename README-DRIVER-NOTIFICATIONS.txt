إصلاح إشعارات السائق — ملفات التعديل فقط

التركيب:
1. شغّل DRIVER-NOTIFICATIONS-FIX.sql في Supabase > SQL Editor بعد التحديثات السابقة.
2. استبدل ملفات HTML وJS الموجودة في الحزمة داخل مجلد الموقع نفسه، ثم انشرها. لا تعيد تشغيل ملفات النقل القديمة بعد هذا التحديث.
3. افتح واجهة السائق بالحساب المعتمد. اضغط «تشغيل إشعارات الموبايل» واسمح بالإشعارات، واضغط «تحديث الموقع» واسمح بـGPS.
4. خلّ حالة السائق «متصل الآن». أرسل طلبًا جديدًا من حساب زبون آخر، بنوع المركبة المطابق، ونقطة انطلاق ضمن 1 كم من موقع السائق. جرّب وصول الإشعار والتطبيق بالخلفية.

يشمل التكسي والتكتك والمندوب والستوتة والحمل، والتوصيل بسيارة أو تكتك، وطلب مندوب المتجر. يعمل بكل العراق ويُبقي شرط القرب الحالي 1 كم. لا يشترط وجود رصيد. الحساب غير المعتمد أو الموقوف أو السائق غير المتصل لا يستلم طلبات جديدة.

التغييرات:
- اعتماد حساب السائق من الملف أو طلب الانضمام الموافق عليه؛ لا يقتصر حفظ GPS على وجود صف transport_profiles معتمد.
- حفظ موقع السائق عند الدخول وتحديثه أثناء فتح الصفحة وعند الرجوع أو استعادة الإنترنت، مع إظهار أخطاء GPS والحفظ.
- مزامنة «متصل/غير متصل» مع إعداد السائق المحفوظ. تغيير الاتصال وحده لا يجدد عمر موقع GPS قديم.
- الطلب الذي لم يجد أي سائق يمكن إعادة تبليغه بنفس الرقم؛ لا يُعد إشعارًا ناجحًا بمجرد حجز رقم الطلب.
- حفظ تبليغ الطلب المعلق بعد فشل الاتصال وإعادة المحاولة. بعد إعادة فتح الصفحة يتم التأكد من أن الرحلة لا تزال searching في Firebase قبل إعادة التبليغ. إعادة التبليغ لا تنشئ رحلة ثانية.
- إنشاء الإشعار بعنوان ونص ونوع ورابط فتح الطلب، وربطه بمسار الإرسال الخارجي الموجود.
- إشعار طلب مندوب المتجر يأتي من جدول توصيل المتاجر ويعتمد موقع الاستلام ومندوبًا معتمدًا متصلًا ضمن 1 كم.
- منع تكرار إشعار نفس الطلب لنفس السائق، حتى إذا حذف الإشعار. إعادة تشغيل SQL لا يكرر الإشعارات.
- يُعيد SQL إنشاء الإشعارات المفقودة لتوصيلات المتاجر المتاحة خلال آخر 15 دقيقة فقط، ولا يعيد تبليغ رحلات Firebase القديمة تلقائيًا.

هذه الحزمة تكمل تعديل مقدم الخدمة السابق ولا تستبدل ملف SQL الخاص به. ملفات notifications.js وfirebase-messaging-sw.js تحتفظ بإصلاح ربط الجهاز بالحساب والعرض على الموبايل من الحزمة السابقة. ملفات التسوق الخاصة بإلغاء الطلب وتغيير المندوب والتوصيل من المتجر محفوظة.

إذا لم يصل إشعار خارجي رغم ظهور الإشعار داخل الموقع:
اقرأ سجل آخر الإشعارات في SQL Editor:
select id,user_id,kind,title,link,push_sent_at,push_attempted_at,push_error
from public.notifications where department='transport' order by created_at desc limit 20;

no_registered_devices يعني أن جهاز السائق غير مربوط بحسابه: فعّل الإشعارات من حسابه ثم اختبر طلبًا جديدًا.
راجع Logs لدالة send-fcm-push إذا ظهر خطأ Firebase أو لم يظهر push_attempted_at. إعداد الإرسال الموجود بالمشروع يستلزم أن يكون Verify JWT with legacy secret مغلقًا لهذه الدالة، كما في إعداد الإشعارات السابق.
إذا ظهر أن المتصفح لا يدعم إشعارات الويب، فنسخة تطبيق الموبايل تحتاج دعم الإشعارات من ملفات Android نفسها؛ هذه الحزمة تعدّل الموقع وقاعدة البيانات.

التحقق: اختبارات SQL الفعلي، اختيار السائق حسب الاعتماد والنوع والقرب والاتصال، شرط الرصيد القديم، إعادة تبليغ الطلب، إشعار مندوب المتجر، واجهة المندوب وGPS وربط الجهاز، ومسارات الطلب الخمسة. إرسال FCM وFirebase معزول في الاختبارات. لم يتم إرسال إشعار فعلي إلى موبايل أو تعديل قاعدة البيانات الحية.
